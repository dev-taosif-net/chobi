# Benchmarks

Numbers are **measured**, not estimated. Targets are engineering goals, not guarantees; misses
are reported as misses.

## Reference machine (Linux)

| | |
|---|---|
| CPU | AMD Ryzen 7 4700U (8 threads) |
| GPU | AMD Renoir / Radeon Vega (Mesa radeonsi, VA-API) |
| RAM | 14 GB (about 10 GB in use by other apps during the run) |
| OS | Ubuntu 26.04 LTS, kernel 7.0, GNOME on **Wayland** |
| Stack | Qt 6.10.2, mpv/libmpv 0.41.0 (client API 2.5), FFmpeg 8.0.1 |
| Build | Chobi 0.1.0, RelWithDebInfo, GCC 15.2 |

Media: 60 s synthetic clips, 1920×1080 at 30 fps; H.264 High (CRF 20, about 7 Mbit/s) and HEVC Main10
(about 6 Mbit/s), each with AAC audio. They are generated by ffmpeg `testsrc2`, which is heavier to
decode than typical film content.

Run: `python3 bench/run_bench.py --runs 5 --seconds 8 --baseline-mpv media...` (medians of 5
launches; warm page cache, because a cold cache needs root to drop).

## Results: Linux, 2026-10-29

### Startup (ms since `main()`, median of 5, warm)

| Mark | H.264 1080p | HEVC10 1080p | Target |
|---|---|---|---|
| QApplication created | 88 | 85 | |
| Engine (libmpv) ready | 91 | 88 | |
| Window shown | 184 | 182 | < 500 ✅ (warm; cold not yet measured) |
| File loaded | 213 | 209 | |
| First frame painted | 351 | 321 | |
| Open → first frame (from "window shown") | 168 | 140 | < 300 ✅ |
| Process wall time incl. exit | 447 | 439 | |

Hardware decoding was active in every run (`hwdec vaapi`, zero-copy EGL import).

### Steady state (8 s window after 2 s settle)

| Scenario | RSS | PSS | CPU (% of one core) |
|---|---|---|---|
| Chobi idle, no file | 186 MB | 131 MB | **0.0** |
| Chobi playing H.264 1080p | 230 MB | 174 MB | 13.1 |
| `mpv --no-config --hwdec=vaapi`, same file | 215 MB | 166 MB | 17.5 |
| Chobi playing HEVC10 1080p | 225 MB | 168 MB | 11.7 |
| `mpv --no-config --hwdec=vaapi`, same file | 210 MB | 162 MB | 10.0 |

Shell overhead versus stock mpv: **+6 to +8 MB PSS, −4.4 to +1.7 % CPU** (budget: ≤ +40 MB,
≤ +3 %) ✅

### Memory stability

100 consecutive file switches (headless engine, after 10 warm-up switches):
**+1.9 MB RSS** (target < 5 MB) ✅. Measured by `test_mpv_engine repeatedFileSwitchingIsStable`.

### Seeking and track switching (headless engine, 12 s H.264 clip)

| Operation | Time |
|---|---|
| Exact seek, command → frame ready | 0–8 ms |
| Audio-track switch (mpv confirms new track while playing) | 252 ms |

### Misses and explanations

- **Idle memory target (< 80 MB) missed: 186 MB RSS / 131 MB PSS.** Breakdown of the idle process:
  Mesa's LLVM 43 MB RSS (24 MB PSS), process heap 27 MB, Mesa gallium 12.5 MB, Qt Gui/Widgets/Core
  15 MB, GTK3 (pulled in by Qt's GNOME theme plugin) 5 MB, libmpv + FFmpeg about 7 MB. Most of this is
  the GPU driver stack, which any GL/Vulkan video player loads. Stock mpv uses 162–166 MB PSS while
  playing. Experiment: hiding the video surface until the first file does **not** avoid loading
  Mesa (the window still composites with GL); creating the GL widget lazily is a possible follow-up.
- Startup is about 85 ms in `QApplication` construction (Wayland connection, fonts, D-Bus/portal,
  accessibility bus) and about 90 ms for window and GL/EGL setup. The GTK theme plugin is *not* the
  cause: switching `QT_QPA_PLATFORMTHEME` changed nothing measurable.
